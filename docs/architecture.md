# アーキテクチャ仮説 — Strata Cascades（仮称）

ここに書くのは**検証前の仮説**である。実装も計測もまだない。各仮説は
[roadmap](../research/roadmap.md) のスパイクで確かめ、外れたらこの文書を書き換える。

## 出発点

3つの目標は、別々の理由で同じ結論を指す。

| 目標 | 帰結 |
|---|---|
| WebGPU / WebGL2 | ハードウェアレイトレーシングが使えない。トレースはソフトウェア前提。WebGL2 はコンピュートシェーダもないので、テクスチャ間パスで組める必要がある |
| スタイル混在 | トゥーンのランプは閾値処理で、小さなノイズを帯境界のちらつきに増幅する。「不偏」より「無ノイズ」が要る |
| 完全動的 | 履歴に頼ると遅延とゴーストが出る。毎フレーム決定的に解ける手法が有利 |

この条件に合うのは Radiance Cascades（RC）系である。確率的サンプリングなしで無ノイズ、
光源数に依存しない固定コスト、フラグメントシェーダだけでも実装できる。

## 仮説

- **H1（場）**：可視サーフェス近傍だけに置いた疎なプローブと RC の区間合成で、
  履歴なしに無ノイズの拡散放射輝度場が得られる。プローブはワールド格子にスナップする
  （2026-11-13 改訂。スクリーン配置はカメラ移動でちらつくことが先行研究で繰り返し
  報告されている。下の「先行研究との関係」）。
- **H2（区間トレーサ）**：区間ごとにシーン表現を切り替えれば、ハードウェア
  レイトレーシングなしで画面外の光と遮蔽を扱える。（S2 で支持。ただし結果として全区間をボクセルにした）
- **H3（ストラタ）**：ハッシュで引く多層ボクセルブリックを区間長に揃えると、
  光線コストとメモリがワールドの広さと三角形数に依存しなくなる。（S2 で部分的に支持：トレースとメモリは
  三角形数によらず、メモリは有界。層は区間長ではなく錐の太さに揃える。作り直しの時間は三角形数に依存する）
- **H4（更新）**：遠い層ほど更新頻度を下げてよく、総更新コストは最下層の約2倍に収まる。（S2 では未測定。
  全層の作り直しは最下層だけの 1.5 倍だった）
- **H5（スタイル）**：スタイルを輸送の両端の演算子として定義すれば、輸送を共有した
  まま写実と非写実を混在でき、写実部分の正しさも保てる。

## 構成

### 放射輝度場

- プローブは可視画素から最寄りのワールド格子点を取り、ハッシュで疎に持つ（Split RC の
  Sparse RC と同じ置き方）。カメラ距離で LOD を変えて画面上の大きさを揃える。
  スクリーン配置は S1 の比較用ベースラインとして残す。
- カスケードが上がるごとに空間解像度を 1/2、角度解像度を 4 倍、区間長を 4 倍にする
  （l = 4。Split RC 付録 A、Gavras、three-rc のいずれも ×4 を採っている）。
- 各カスケードは距離区間 `[t_i, t_{i+1}]` だけをトレースし、上位カスケードと合成する。
- **区間の埋め方は S1 で比べる**：プローブ方向ごとに決定的にトレースする素の RC（無ノイズ、
  光線数はカスケード数倍）と、画素から 1 本ずつ撃って区間に振り分ける Split RC の
  レイ分割（光線数 1/N、ただしジッタ付きの確率的サンプリングで 1 フレームでは少し
  ノイズが残る）。R4（ランプを通してもちらつかない）に効くのは前者の性質である。
- 履歴は原則持たない。多重バウンスは前フレームの照明結果をヒット点の放射輝度として
  読むことで得る。
- **S1 の結果（2026-11-13、[記録](../research/spikes/s1-sparse-cascades.md)）**：ワールド格子配置は
  配置由来のちらつきを測定の床まで下げ、スクリーン配置より安定だった。区間は方向ごとの決定的トレースで
  埋める（レイ分割は静止時でもちらつく）。一方、表面上の疎なプローブは上のカスケードで約 1/3.3 にしか
  減らず、方向は 4 倍になるので、光線数がカスケードごとに増える（体積の RC の想定は 1/2 ずつ減る）。
  予算に入れるには c0 を画面上 32 画素程度まで粗くする必要があった。上のカスケードの角度分解能の伸びを
  抑えるかどうかは未決。
- 最上位区間を抜けた光線は空・環境光を返す。
- **S2 の結果（2026-11-13、[記録](../research/spikes/s2-voxel-stratabrick.md)）**：区間をワールド空間でトレースすると
  太陽だけの移動時ちらつきは 42% → 29% になり、正確な可視性（三角形）でも同じ 29% だった。残りの最大の要因は、
  G-buffer に平面を当ててプローブを面の手前へ押し出す処理が視点に依存すること（止めると 16〜17%）。押し出しを
  ワールドの表現（ボクセルの占有など）から決めるのが次の課題。上のカスケードの方向は c2（64 方向）で止めても
  誤差とちらつきがほぼ変わらず、トレースが半分になる。

### 区間トレーサ

インターフェースは1つにする：`trace(origin, dir, t0, t1) -> (radiance, transmittance)`。
合成側はトレーサの実体を知らない。これがプラットフォームのティア分けの継ぎ目になる。

| 区間 | 表現 | 動的対応 |
|---|---|---|
| 近距離 | ボクセル StrataBrick（S2 で決めた） | 深度バッファ（S1）は画面外へ出た光線が空になり、空ありで 18 倍明るく、太陽だけで移動時 42% ちらつく。c0 だけ深度バッファにしても誤差は同じでちらつきは増えた。c0 の接触遮蔽はボクセルでは取れない |
| 中〜遠距離 | ボクセル StrataBrick の層 L | S2 は全層を毎フレーム作り直した（Sponza 1.9 ms）。動いた物体のブリックだけの更新は未実装 |
| 任意（ネイティブ、将来の WebGPU ray query） | BVH | 同じインターフェースで差し替え |

### ボクセル StrataBrick

Program 1 の StrataBrick（[legacy/stratabrick/](../legacy/stratabrick/)）から上位構造を
引き継ぎ、中身を替える。

- **引き継ぐもの**：固定サイズのワールドブリックをハッシュで引き、光線は DDA で渡る。
  ブリック単位で所有し、局所的に更新する。B003 では上位を BVH8 に替えると 2.17 倍
  遅くなり、この上位構造は替えるべきでないと結論している。
- **替えるもの**：ブリックの中身を三角形 BVH から、占有ビットマスクと放射輝度の
  ボクセルにする。三角形 BVH は CPU 構築が重く（Sponza で約 115 ms）、コストが三角形数に
  比例するため、Web と高密度の両方に向かない。
- **多層化**：層 L のブリックサイズを 2^L 倍にする。区間長がカスケードごとに 4 倍に
  なるので（l = 4）、カスケード i を層 2i に対応させるか、層 i で渡るブリック数が 2^i で
  増えるのを受け入れるかを S2 で決める。前者なら 1 区間で渡るブリック数が一定になる
  （2026-11-13 改訂。当初は区間長 2 倍を暗黙に仮定していた）。→ S2 で後者（層 i）に決めた。
  前者はボクセルが錐より粗くなり、遮蔽の過大で誤差が大きい。
- **ブリック内部**：Godot HDDAGI の 3 段構成（8³ 領域の使用フラグ → 4³ ブロックの
  64 ビット占有マスク → ボクセル）と、分岐しない 1 本のループで書く階層 DDA を手本にする。
- **カメラ相対クリップマップ**：各層は占有ブリックだけを持つ。メモリは
  「層数 × 層あたり占有数」で、ワールドの広さと無関係。ブリックはそのまま
  ストリーミングの単位になる。
- **遠い層の中身**：被覆率と平均放射輝度。サブボクセルの密なジオメトリは統計量として
  持つ。
- **方向別不透明度**（検証対象）：ボクセルより薄い壁を、法線方向には不透明、面内方向
  には透明として持ち、粗い層のリークを抑える。

三角形版は捨てない。ボクセル近似の可視性誤差を測る正解器として使う。

**S2 で作ったもの（2026-11-13、[記録](../research/spikes/s2-voxel-stratabrick.md)）**。上の案との違いを書く。

- ブリックは 8³ ボクセル、占有ビット 16 語。Godot HDDAGI の 3 段ではなく 2 段（ブリック → ボクセル）の DDA で、
  空ブリックを丸ごと飛ばす。区間あたり 3〜12 ステップ。
- 各層はハッシュでなく、カメラ相対の 64³ のブリックポインタ（密、1 MiB / 層）＋占有ブリックのプール。メモリは
  有界で、Sponza で常駐 12.8 MiB、構築用 18.6 MiB。
- ボクセルは被覆率や平均放射輝度ではなく、代表三角形の albedo と法線を持ち、ヒット時に太陽の影を引く。
  薄い壁をまたぐボクセルは、影をレイ側（ボクセルの入口）で引くことで外側の光を拾わない。
- 層の対応は**カスケードごとに 1 層**（c0 のボクセル = 0.25 × c0 プローブ間隔）。2 層ずつは誤差 −37〜−57%。
- 誤差は遮蔽の過大の側（三角形との差 −8〜−16%）。リークは三角形より少ない。方向別不透明度は試していない。

### 動的更新

- 剛体はオブジェクト局所のブリックを一度作り、変換してワールド格子に書き込む
  （Lane E の方式、[legacy/object-local/](../legacy/object-local/)）。
- 変形する物体だけ再ボクセル化する。
- 層 L の形状更新は 1/2^L の頻度にする（H4）。光源の点滅のような時間変化は距離で
  減衰しないので、放射輝度の更新は形状と分けて毎フレーム行う。
- S2 は全層を毎フレーム三角形から作り直した（Sponza 26 万三角形で 1.89 ms、236〜262 万三角形で 3.6〜4.2 ms）。
  M2 の規模では上の局所更新が必須。

### スタイル演算子

輸送は線形のまま共有し、スタイルは次の2か所にだけ作用する。

- **放出側**：その面が場に何を注入するか。トゥーンの物体は帯で塗った色を注入する、
  彩度を誇張する、バウンスしない、など。
- **受光側**：場のサンプルをどう陰影に写すか。場から「環境色、支配方向、方向色、
  遮蔽」を取り出す。写実材質は BRDF で積分し、トゥーン材質は支配方向を仮想の
  キーライトとしてランプに通す。
- **ライトグループ**（任意）：場を少数のチャンネルに分け、ライトリンクを表現する。

輸送が線形なので重ね合わせが成り立つ。写実の物体は、隣に非写実の物体がいても物理的に
正しいままである。放出側スタイル適用後の放射輝度をブリックに格納すれば、画面外の
非写実物体からの照り返しも同じ仕組みで扱える。

| ティア | 区間トレーサ |
|---|---|
| WebGL2 | スクリーン空間のみ＋空・環境のフォールバック |
| WebGPU | ＋ボクセル StrataBrick |
| ネイティブ / 将来の ray query | 中距離を BVH に置換 |

## 未決事項

- ツールチェーン（S0 で決める）。候補は C++ と Dawn（ネイティブとブラウザで同じ
  シェーダ）、Rust と wgpu、ブラウザ直書きの TypeScript。
- ブリックのバイト数と層あたりの占有数。メモリ見積もりは未実測。
- 回転する剛体をワールド格子に書き直すときの滲み。足りなければオブジェクト空間で
  直接トレースする二段構造にする。
- RC 固有のアーティファクト（リンギング、硬い影のぼけ）への対処。

## 先行研究との関係

部品には先行がある。スクリーン空間 RC（Path of Exile 2）、GI 対応スタイライズ
（Doi ら, Pacific Graphics 2021、本文未確認）、および下の 5 件。貢献になり得るのは、
スタイルを場の演算子として定式化すること、ハードウェアレイトレーシングなしの Web 前提の
区間トレーサ階層（区間長に揃えたボクセル層）、混在スタイルの評価法である。

2026-11-13 に一次資料（本文、ソース、提案文書）を確認した。数値は各著者の自己申告で、
こちらでは再現していない。

| 先行 | 要点 | 仮説への影響 |
|---|---|---|
| Split Radiance Cascades（Freeman, Sannikov, Pitt-Francis, arXiv 2607.20384 v2） | 可視画素から最寄りのワールド格子プローブをハッシュに登録（カスケードごと、LOD 付き）。画素から 1 本ずつ光線を撃ち、ヒット距離で区間に振り分ける（レイ分割）。l = K = 4、c0 は 32 方向、4 カスケード。OptiX（HWRT）。単一フレームで Sponza 8.6 ms（G-buffer と影を除く、RTX 3080 Laptop）。うち deposit 2.2 ms、shade 2.5 ms で、トレース（1.3 ms）以外が重い。可動物体の時間蓄積は未対応、リークはマージ時の補間で出る、c0 間隔より小さい物体は落ちる（画面空間の C(-1) で補う） | 最も近い先行。H1 のプローブ配置をこれに寄せた。差分は HWRT なし、区間ごとのトレーサ切替、スタイル演算子。HWRT ありの dGPU で 8.6 ms なので、8060S で 4 ms は厳しいと見ておく |
| Gavras, "Exploration and Optimization of Radiance Cascades for Real-Time Applications"（Chalmers 修士, 2025） | スクリーン配置プローブ＋ワールド空間区間（SPWI）。全区間を三角形 BVH でトレース。1080p Sponza 144 ms（M1）。履歴なし。画面外の光は取れる。**カメラ移動でちらつく**のが最大の未解決点 | スクリーン配置をやめる根拠。全区間を三角形でトレースすると HWRT なしでは桁違いに遅い |
| Abou Dan & Jensen, "Screen Space Global Illumination Using Radiance Cascades in 3D Video Games"（Chalmers 修士, 2025） | スクリーン配置＋可視性ビットマスク GI でスクリーン空間トレース。2〜26 ms。履歴なし。画面外は扱えない。小さな動きでもちらつく。**本文は公開されておらず、要旨のみ確認** | 近距離を深度バッファだけで済ませると画面外の遮蔽が抜けて明るすぎる。中〜遠距離のワールド表現が要る |
| Godot HDDAGI（godotengine/godot #86267 ほか。2026-11 時点で未マージ） | カメラ中心のカスケード（セル 2 倍ずつ）、各カスケード内は 8³ 領域 → 4³ ブロックの 64 ビット占有マスク → ボクセルの 3 段。分岐しない階層 DDA。プローブは格子配置で 6〜32 フレームかけて収束、光の注入も数フレームに分散。動的物体は場に寄与しない。GTX 1650 でプローブトレースと光の更新 0.93 ms | H3 のボクセル部分にほぼ一致する先行。ブリック内部の構造はこれを手本にする。新規性は「区間長に揃えた層」と「動的物体の寄与」「履歴なし」の側に残る |
| three-rc（CodyJasonBennett/three-rc、WebGL2、ライセンスなし） | スクリーン配置プローブ、区間 ×4、フラグメントシェーダで BVH をスタック走査。作者自身が WebGL での BVH 走査は実用的でないとし、WebGL ではスクリーン空間トレースを勧めている。深度不連続でちらつく | WebGL2 ティアをスクリーン空間のみとする方針を支持。コードはライセンスがないので流用しない |
| gpuweb ray query（#11053〜#11056、2026-10-13 提出） | 2026-10-27 の WGSL 会合で「提案として取り込む」と決定、大幅な改訂が必要とされた。仕様本文には未収録。Dawn に実装なし。wgpu は Vulkan ネイティブのみ実験機能 | BVH ティアは当面ネイティブ限定の将来枠のまま |

共通して、履歴を持たない RC 実装は**カメラ移動時のちらつき**を最大の問題として挙げている。
R4 にとって最も大きなリスクで、S1 では静止時だけでなくカメラ移動時のちらつき率を測る。
