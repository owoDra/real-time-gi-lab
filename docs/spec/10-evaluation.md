# 評価方法

## 原則

1. **同じコストでの品質を比べる。** 予算を固定し、その中での品質と対応範囲を測る。
2. **探索と確認を分ける。** 探索では事前登録をしない。数値は「探索値」と明記する。確認実験は最後に 1 回、条件、
   比較相手、指標、判定規則を先に書いてコミットしてから測る。結果を見てから閾値を変えない。
3. **実用に近い条件で測る。** RGB、テクスチャ付き、フル解像度。
4. **データの健全性を先に確かめる。**（下の「健全性チェック」）

## 指標

| 対象 | 指標 | 測り方 |
|---|---|---|
| 写実品質 | 放射照度の相対誤差 Σ\|ours − ref\| / Σref と平均の偏り | 参照（Mitsuba）との比較。非写実物体は放出側プロキシに置き換えたシーンを参照にする |
| 写実品質（動く物体の画素） | 同じ誤差と偏りを、動く物体（写実の材質）の画素だけで | 上の比較は建物の画素だけを数える。物体の画素は放射照度のダンプの印（2）で分け、`ref:compare -- --objects` で別に出す（2026-11-15、Phase 27）。物体が写実の場面（`-objects`、`-dynobj…`）だけ。姿勢を止めて比べる |
| 時間安定性 | 帯境界ちらつき率 | 連続フレーム間に量子化帯が変わる画素の割合。間接放射照度の輝度を log2 で 1/4 段（細）と 1 段（粗）の帯にし、カメラ移動時は前フレームへ再投影して同じ面の画素だけ数える。ワールド固定の対照場で測定の床を併記する（`src/core/post.ts`）。**カメラが動く場面と建物が動く場面では、法線マップを外した実行の値を主に読む**（下の「法線マップを外した値」） |
| 時間安定性（動的シーン） | 超過変動（静止カメラ） | 画素ごとに、窓 K フレーム（K = 16 が既定、8 と 32 を併記。フレーム番号で揃えた重ならない窓）で、l = log2(間接放射照度の輝度)（帯と同じ下限 10⁻³）の Σ\|Δl\| − \|l_end − l_start\| を取り、K − 1 で割って画素と窓で平均する（段 / フレーム）。窓のどこかのフレームで動的物体か無効だった画素は、その窓を数えない。確認用に、同じ量を線形の輝度で取って窓の平均の輝度で割った値（相対）を K = 16 で併記する。帯境界ちらつき率も、両フレームとも動的物体でない画素だけで併記する（`staticFinePct`）。`src/core/post.ts` |
| 時間安定性（動的シーン、移動カメラ） | 移動カメラの超過変動（K = 16） | 画素ごとに窓の状態（前フレームの l、窓の始めの l、Σ\|Δl\|）を、前フレームの再投影先の画素（帯境界ちらつき率と同じ判定）から毎フレーム引き継ぎ、窓（フレーム番号で揃えた K = 16）の始めで作り直す。窓の途中で再投影が外れたか、無効か、動的物体だった鎖は数えない。あとは静止カメラと同じ（段 / フレーム、線形の相対値を併記）。同じ鎖でワールド固定の対照場の値（`controlExcessPerFrame`）を取る。静止カメラでは静止カメラの K = 16 と一致する（法線の判定で外れる短い法線の画素の分だけ違う：`sponza-dynobj` で 0.01193 / 0.01192）。`src/core/post.ts` |
| スタイル | トゥーンのランプの帯の切り替わり | 方向成分が環境の 10% 以上ある画素で、受光ランプの帯が変わった割合。固定方向に対する対照を併記する |
| 応答性 | 光源切替後、差が 50% / 10% 以下になるまでのフレーム数 | Σ\|E_t − E_end\| / Σ\|E_before − E_end\|（写実の画素の輝度、静止カメラ）。**E_end は、切り替えの後の姿勢を止めて収束させた放射照度**（2026-11-15、Phase 27。下の「応答の終わりの値」）。切り替えの後 64 フレームは毎フレーム、その先は 8 フレームおきに読む（`--response FROM,TO`、`src/core/rcrun.ts`） |
| 遅れ | 動かしてそのフレームに着いた放射照度と、姿勢を止めて収束させた放射照度の、参照に対する誤差の差 | 姿勢ごとに参照を描く |
| リーク | 閉じた部屋の中の平均照度を、外の床の太陽照度に対する割合で | 壁の厚み 0.02〜0.4 m |
| 黒い欠け（RC） | 8 つの c0 プローブがすべて遮られた写実の画素の割合 | gather の遮り判定で 8 つとも遮られ、2 ボクセル先からの再試行でも遮られた画素を GPU で数える（最後のフレーム、実行器の `black pixels`。2026-11-15、Phase 29。Phase 28 のダンプから数えた値と同じ） |
| 広さ非依存（R2） | ワールドを 10 倍・100 倍にしたときの時間とメモリの変化 | |
| 密度非依存（R3） | 表面積を保って三角形を 10 倍にしたときの時間の変化 | |
| ストリーミング | 高速移動時のフレーム時間スパイク | |
| コスト | GPU 時間（タイムスタンプ）、GPU メモリ（確保した合計と使用量。真のピークは未計測） | |

### 動的シーンのちらつきの読み方

- 物体や光源が動くシーンの帯境界ちらつき率は、**本物の変化を含む**。小さな変化では、ちらつき率は
  「1 フレームの平均 \|Δlog2 E\| ÷ 帯の幅」にほぼ等しい（細帯 0.25 段）。
- **時間平均を持つ手法（DDGI 系）の値を「本物の変化の上限」として使わない。** 時間平均は、仕様どおりの離散的な変化
  （放出側トゥーンの帯の切り替わりなど）も均してしまう。
- 代わりに**超過変動**を使う：窓 K フレームで Σ\|Δl\| − \|l_end − l_start\|。滑らかな一方向の変化では 0 に近く、
  往復する跳びだけが残る。動的物体の画素と、その遮蔽・露出の画素は数えない。
- 正規化は log2 にした（2026-11-14）。帯境界ちらつき率と同じ尺度で、明るさの違う面と手法を並べられるため。
  log2 は暗い面の小さな変化を重く数えるので、線形の相対値を併記して、結論が暗い面だけで決まっていないことを確かめる。
- 移動カメラの超過変動（2026-11-14、Phase 15）は、鎖が最も近い画素への再投影で 1 フレームに半画素までずれるので、
  法線マップや材質の細部で放射照度が画素ごとに違う面では、手法と関係のない値が乗る。ワールド固定の対照場（法線への
  依存が弱い）は 0.007〜0.008 段 / フレームで、この床を表しきれない。静的な `sponza` で DDGI（静止カメラでは 0.002）が
  0.042 段 / フレーム（線形 0.037）を示すので、実際の床はその程度と見ている（未検証）。手法の差は、同じ場面の DDGI との
  差と、線形の相対値で読む。移動カメラで物体や光源が動くシーンの帯境界ちらつき率は本物の変化を含むので、手法の優劣の
  判定には使わない。
- 更新を遅らせる実験（層ごとの更新頻度を下げる）は、総変動を減らさず特定のフレームへ集めるだけなので、
  ちらつきの原因の切り分けには使えない。切り分けはマスク（その要素を完全に外す）で行う。

### 法線マップを外した値（2026-11-15、Phase 27、AI の決定）

- ちらつきと超過変動は、画面の同じ画素（静止カメラ）か再投影した画素（移動カメラ）の放射照度を前のフレームと比べる。カメラか面が動くと、
  その画素は法線マップの別のテクセルに当たり、放射照度は法線に依るので、場が変わらなくても値が変わる。手法と関係のない見かけで、
  RC にも DDGI 系にも同じように乗る（静的な `sponza` の移動カメラで細帯 19.0 / 15.6% のうち 15.7 / 12.1 ポイント。建物が波打つ場面の
  静止カメラの超過変動で 0.064 / 0.067）。
- 実行器は同じ場面を、G-buffer の法線を法線マップなし（頂点の法線の補間）にしてもう一度回し、ちらつきと超過変動を両方出す
  （要約の `staticGeo`、`movingGeo`。場は作り直すので、履歴を持つ手法も同じ初期状態から始まる）。**移動カメラと、建物が動く場面
  （`-bwave`）では、法線マップを外した値を主な値にし**、法線マップありの値を併記する。最終画像と GI の時間は法線マップありの実行のもの。
- 面が画面の上で動かない場面（静止カメラで、建物が止まっているか一部が現れて消える）では、2 つの値は一致する
  （`sponza-dynobj` 0.01126 / 0.01126、`sponza-dynobj-n64-deform-bcut` 0.0345 / 0.0345）。
- 法線マップを外した移動カメラの対照場は細帯 0.93%、鎖の超過変動 0.0013（静的な `sponza`）。これが再投影の半画素のずれだけの床。
- 放射照度の値そのもの（参照との誤差、応答）は、法線マップありのまま測る。

### 応答の終わりの値（2026-11-15、Phase 27、AI の決定）

- Phase 26 までは実行の最後のフレームを E_end に使っていた。履歴の長い手法は実行の終わりでもまだ動いているので、曲線が実行の長さに
  合わせて 0 に着き、短く出た（DDGI 線形 `ddgi-100-128-u8-g1-noadapt`：切り替えの後 120 フレームの実行で 90、320 フレームで 268、直した値は 712）。
- 直した形：フレーム TO の姿勢を止めたまま 1008 フレームの窓を続け（9 フレームおきに読む）、窓の平均の放射照度（画素の和）が前の窓から
  1% 未満しか変わらなくなった窓の、画素ごとの平均を E_end にする（最大 8 窓。届かなければ `end.converged` が false）。最初の 8 回の読みが
  完全に同じ場（乱数の無い RC。Phase 29 の c0 の短い履歴も、止めた姿勢で数フレームのうちに同じ値に止まる）は、その値をそのまま使う。
- 判定を「画素ごとの差が 0.1% 未満」にしなかった理由：確率的な場は収束した後も画素ごとには変わり続ける（7 フレームの平均どうしの差が
  DDGI 線形で 1%、速い設定で 7〜9%）。窓の和でも速い設定は ±0.5〜1% 揺れるので、1% にした。DDGI 線形は切り替えの 60 フレーム後から
  約 1600 フレーム、和が一方向に動き続ける（多重バウンスが遅い履歴を何度も通る）ので、この判定で収束の前と後を分けられる。
- TO は 10% に着くより後に置く（着かなければ `frames90` は null）。DDGI 線形は `--response 200,2600`、ほかは `200,520` で測った。

### DDGI 系のウォームアップ（2026-11-15、Phase 27 で気付いた）

既定の計測（ウォームアップ 60 フレーム）では、DDGI 線形の場はまだ収束の途中にある（上の応答で 90% まで 712 フレーム）。静止カメラの超過変動は
一方向の変化を数えないが、収束の途中の値は収束した後より大きく出る（`town-dynobj-bwave` で 0.0074、前の実行から場を引き継ぐと 0.0043）。
静的な場面の参照との誤差は、ウォームアップを 2400 フレームに延ばしてもほぼ同じ（`sponza` の 8 × 8 ブロックで 0.283 → 0.285、偏り −5.0 → −3.4%）。
姿勢を止めて DDGI 系を参照と比べるとき（動く物体の画素）は、ウォームアップ 2400 フレームで測る。

## 比較相手

Web で実現可能なものを相手にする。

- **DDGI 系のプローブ（実装済み、`src/core/ddgi.ts`）。** 同じボクセルの区間トレーサでトレースする。
  構成は [20-renderer.md](20-renderer.md)。RTXGI 既定のガンマ 5 の時間混合は暗い側に偏るので、主な比較には線形の混合
  （設定トークン `g1-noadapt`）を使い、RTXGI 既定も併記する。設定は同じ 4 ms に入る中で選び直す（2026-11-15、Phase 25：線形は
  `ddgi-100-128-u8-g1-noadapt`、RTXGI 既定は `ddgi-100-128-u8`。試した範囲は [30-measurements.md](30-measurements.md) の 29 節）。
  DDGI 系は応答と安定が引き換えなので、1 つの設定ではなく並びで比べる（2026-11-15、Phase 26）：上の線形に加えて、応答の速い
  `ddgi-100-128-u8-h0.5-g1-noadapt`、`ddgi-150-64-u1-h0.8-g1-noadapt`、`ddgi-125-64-u2-h0.5-g1-noadapt`（30 節）。
- スクリーン空間 GI（SSGI）：未実装。
- ボクセルコーントレーシング：未実装。
- 参考：Program 1 の Split RC レンダラ（ネイティブ、HWRT。タグ `archive/program-1`）。

**明るさの正しさは参照（Mitsuba）で言う**（2026-11-14）。三角形 BVH のトレーサはボクセル近似の影響を分ける用途に限る。
方向ビン 1 本のレイなど RC そのものの偏りを共有していて、物体の近くの床では参照の 0.53〜0.84 倍と暗かった
（[30-measurements.md](30-measurements.md) の 13 節）。

一方にだけ入れた改良で比べない。場の前置フィルタのように両方に効く改良は、両方に入れてから比べる
（[40-dynamic-stability.md](40-dynamic-stability.md)）。

## 健全性チェック（必須）

Program 1 では「光源移動」と名付けたシーケンスが全フレーム同一で、「剛体運動」の 6 本が画像上は静止していた
（[記録](../reference/program-1/dev-sequence-validity-check.md)）。再発させない。

- 動的シーケンスを作ったら、**参照画像がフレーム間で参照ノイズを超えて変化すること**を生成時に assert する。
- 動く物体がカメラから見えていることを確認する。
- 建物が変わる場面（`-bwave`、`-bcut`）は、静止カメラの最初と最後のフレームで最終画像の 0.5% 以上の画素が変わることを実行時に確かめ、
  満たさなければ止まる（Phase 20 で 22〜37%）。
- 新しいシーンと新しい結果は、数値だけでなく**画像を目で見る**。
- 「最良の比較相手」と書くときは、試した設定の範囲を併記する。
- 以前の数値を前提にする実験は、最初にその数値を再現する。

## 計測の作法

- 性能判断は GPU タイムスタンプで行う。CPU の壁時計は補助。
- 既定の計測：1080p、ウォームアップ 60 ＋ 240 フレーム、同時に 2 フレームまで投入、静止カメラと移動カメラ
  （240 フレーム、毎フレーム前へ 2.5 cm、横へ ±0.4 m、ヨー ±12°）。GPU のクロックは固定しない。時間は実行ごとに
  20% 程度ずれる。
- GPU ジョブは同時に 1 本。参照（Mitsuba、CPU 32 スレッド）を描いている間は GPU 時間を測らない（同じ電力枠を使う）。
- 予算に近い GPU 時間（4 ms に対して 0.5 ms 以内）を書くときは、独立に 3 回測って範囲を書く。
- 確認実験の時間比較は、独立プロセスを複数回、AB/BA の順序を釣り合わせ、中立な対照で最小検出可能効果を先に測る
  （実装はタグ `archive/program-1` の `scripts/research/lane_m_gi_competitiveness/`）。
- 負の結果は残す。短く。

## 参照レンダラ

Mitsuba 3（3.6.4、`llvm_ad_rgb`、CPU）。AI が決め、ユーザーの確認は取っていない。

- 正解器は製品のコードと独立しているほうがよい（同じ誤りを共有しない）。
- シーンはこちらの glTF 読み込みから変換して渡す（`mise run ref:export -- --scene <名前>`、出力は
  `box/out/mitsuba/<名前>`）。アルファマスクと両面材質の解釈を製品側と揃えるため。法線マップは参照側に入れていない。
- 積分器（`scripts/reference_irradiance.py`）は、GI パスの出力と同じ量（可視点の間接放射照度。ヒットごとの太陽の直接光、
  抜けた光線は空）を正確な可視性で積分する。可視点の直接光は含めない。トゥーン材質へのヒットは放出側演算子の値を
  返す（放出側プロキシ）。その先のバウンスではトゥーン材質もアルベドの Lambert として反射する。
- `--bounces 1` は 1 バウンス（Phase 22 までの参照。2026-11-15 に、多重バウンスの版を 1 に絞ると前の参照とビット単位で一致することを確かめた）。
  `--bounces 0` は打ち切りなし（3 回目のヒットからロシアンルーレット）。**Phase 23 から、レンダラは多重バウンスなので、参照との誤差は多重バウンスの参照で言う**
  （1 バウンスの参照に対する値も併記する）。
- 比較は 960×540。1 バウンスは 512 spp × 2 本（各約 5 分）、多重バウンスは 256 spp × 2 本（各約 26 分、`sponza`）。独立な 2 本の差で参照自身のノイズを
  併記する（Sponza で 1 バウンス 17%、多重バウンス 23.5%）。`sponza-dynobj` 姿勢 0 は 1 バウンス 512 spp × 2 本、多重バウンス 128 spp × 2 本。
  `town` は軽い（1 バウンス 512 spp で約 5 秒、多重バウンス 256 spp で約 90 秒）。
- **誤差は 8 × 8 画素（参照の解像度）のブロック平均でも出し、こちらを主に読む**（2026-11-15、Phase 25、AI の決定）。画素ごとの差を参照のノイズより小さく
  するには多重バウンスの Sponza で 1 本 9 時間以上かかる。ブロックで平均すると参照のノイズはおよそ 1/8 になり、独立な 2 本の差は Sponza の多重バウンスで
  3.0%、1 バウンスで 2.2%、`town` で 1.0〜1.3% と目安の 5% を下回る。ブロックは 3/4 以上の画素を比べられるものだけ数える。8 画素は 1080p の 16 画素で、
  離れた所の細かい影は平均で消えるので、細部の正しさは画素ごとの値と並べた画像で見る（`src/native/compare_ref.ts`、16 × 16 も出す）。
