このフェーズは **Claude Fable** で行う（ユーザー 2026-11-14）。新しいセッションで `/model` から Fable を選び、下の
開始プロンプトをそのまま貼る。

## 目的

Program 2 は、同じモデルが続けて計画、実装、計測、判断をしてきた。動的な跳びの対策に Phase 01〜07 を使い、P2 で
物体が動く分の跳びを 95% 減らした。ユーザーはできた物を見て OK とし（2026-11-14）、次に進む前に、別のモデルから
次の点について助言をもらいたいと言った。

- 今後どのように進めるか。
- 本来の趣旨から脱線していないか。
- ほかに問題はないか。
- もっと良い方法はないか。

このフェーズは助言をもらい、方向を決めるためのもの。物はまだ作らない。

## 見直す問い

1. **趣旨からの脱線**：00-overview の目的 1〜3 と R1〜R6 に対して、いまの配分と順番は妥当か。触れていない要件
   （R2 大規模、R3 高密度、R5 スタイル混在の動的な場面、R6 とブラウザでの実行、WebGL2）を後に回していて良いか。
2. **今の結果の問題**：P2 と既定の構成に、見落としている問題はないか。たとえば、物体の近くの遮りが弱い件、動的レイヤの
   上限と毎フレームの作り直しの費用、DDGI 側にも入った動的レイヤが未計測であること、カメラ移動時のちらつき、
   評価の指標（超過変動）と計測の回数、参照（Mitsuba）との誤差。
3. **もっと良い方法**：RC を土台に遅れ 0 の前置フィルタで跳びを抑える方向（2026-11-14 の決定）より良い道はあるか。
   先行研究と、同じ 4 ms・128 MB・WebGPU のコア機能という制約で比べる。
4. **進め方**：次の予定（P1 → built → DDGI 側にも入れて比べ直す → 同じ 4 ms で優位があるかの review）をこのまま進めるか、
   順番を変えるか、方向を変えるか、止めるか。
5. **作業の仕方**：plan 駆動の進め方、フェーズの大きさ、記録の残し方に、直した方が良い所はあるか。

## 決定済みの方針

- 技術の選択はユーザーに求めない。AI が理由をつけて決め、平易に報告する。ユーザーに尋ねるのは目標、予算、できた物の
  見た目の OK だけ（[AGENTS.md](../../../AGENTS.md)）。目標か予算を変えるべきだと考えたら、AskUserQuestion で尋ねる。
- 予算（GI 4 ms、128 MB）と評価の指標は、このフェーズでは変えない。変えるべきだと考えたら理由を書いて尋ねる。
- 確かめるための計測は、画像を変えない計測だけの auto として、このフェーズの中で行ってよい。GPU ジョブは同時に 1 本。
- 結論が「いまの予定のまま進める」でもよい。同意するときも、何を確かめて同意したかを書く。

## 確かめる決定

| 決定 | 確かめ方 |
|---|---|
| 問いの 1〜5 に全部答える | Artifact に問いごとの節がある |
| 主な主張をソースか計測で確かめる | Artifact に、確かめた主張と確かめ方（ファイルと行、コマンドの出力）の一覧がある |
| AI が決め、ユーザーに選ばせない | 報告が決めた方向と理由で終わっている |
| 予算を変えない | spec の予算の記述が変わっていない |
| 決めた方向を還元する | spec（00 の AI の決定、40、50）に日付つきで書き、後のフェーズのファイルを書き直している |

## やること

1. 前提の資料を読み、主な主張をソースで確かめる。必要なら計測だけで確かめる。
2. 問いの 1〜5 への答えと、決めた方向と理由を 1 枚の非公開の Artifact にまとめ、URL をここに書く。ユーザーに平易に
   報告する（専門用語を使うなら最初に 1 文で説明する）。
3. ユーザーが変えたいと言えば従う。
4. 決めた方向を spec に書き、採らなかった案を消し、次のフェーズのファイルを作り、列の表を書き直し、このファイルを消す。
   `box/in/phase07-p2-check/` は、次のフェーズで要らなければ消す。
