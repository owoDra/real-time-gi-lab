## 目的

段階 E。ここまでの値はすべてネイティブ（Dawn / Vulkan）のもの。実際のブラウザで同じ画像が出て、予算に入るかを確かめる（R6）。
GI の余裕は 0.12〜0.17 ms しかなく（Phase 28、空いた機械で 3.83〜3.88 ms。Phase 29 の後の値は Phase 29 が書き直す）、ブラウザがネイティブより 1 割遅ければ予算を割る。割るなら後の段階（物体の跳ね返り、広さと密度）の設計が変わるので、
それらの前に確かめる（2026-11-15、Phase 26、AI 決定）。

## 前提

- ブラウザ用の実行器は消してある（2026-11-13、ネイティブだけで進める決定）。`src/core/` は WebGPU のコア機能だけで書いて
  あり、実行器は WebGPU の既定の上限でデバイスを作っている（2026-11-14、ネイティブで確かめた）。
- 作業機のブラウザの WebGPU はソフトウェア描画（SwiftShader）になる。GPU のサンドボックスを切る起動は許可されなかった。
  **どの機械で確かめるかはユーザーに尋ねる。**
- ブラウザのタイムスタンプは、機能（`timestamp-query`）が無いか、精度が粗いことがある。

## 決定済みの方針

- `src/core/` は変えない（ブラウザのための分岐を入れない）。要るのは実行器と、資産の読み込みだけ。変える必要が出たら、
  それは R6 の欠陥として spec に書く。
- 画像の一致は、同じ場面・同じフレームの間接光を 8 ビットで比べ、平均の差 0.5 段以下を「一致」とする（GPU とドライバが
  違うのでビット単位では求めない）。
- GI の時間は、タイムスタンプが使えればそれで、使えなければフレーム時間の差（GI あり − なし）で測り、測り方と精度を書く。
- 開発機 1 台の結果を一般化しない。確かめた機械とブラウザの名前を必ず添える。

## 確かめる決定と、その確かめ方

| 決定 | 確かめ方 |
|---|---|
| GPU で動いている | ブラウザのアダプタの情報（ソフトウェア描画でないこと）を記録する |
| 画像が一致する | `sponza`、建物が変わり物体 64 個が動く場面の 1 フレーム、トゥーンの物体 |
| 予算 | 同じ機械のネイティブの値と並べて、GI の時間とメモリを書く。建物が波打ち物体 64 個の場面でブラウザの GI が 4.0 ms を超えたら、超えた分と段ごとの内訳を spec 50 の「続けるための条件」の 1 つ目に書き、Phase 31 と 32 のファイルの余裕の前提を書き直す（予算は変えない） |
| 既定の上限 | 上限を上げずにデバイスを作れている |

## やること

1. 実行器を作る（最小のページ。場面と設定は URL の引数）。
2. 作業機で動くか確かめる（ソフトウェア描画でも、画像の一致までは確かめられる）。
3. GPU で動く機械で確かめる（ユーザーに尋ねる）。
4. 還元：spec 20（ティアの表）、30、50、[project-structure.md](../../project-structure.md)、要約。後のフェーズ（31〜33）の前提を書き直す。
