# 作業計画

この `docs/plan/` は作業を進めるための計画で、正本ではない。目的・評価・構成・測った結果・方向の正本は
[`docs/spec/`](../spec/README.md)、挙動の正本はソースとコメントである。計画と実装が食い違ったら実装を確かめ、
計画の誤りに気付いたらユーザーに伝える。

パスはリポジトリのルートからの相対で書く。実行の出力は `box/out/`、ユーザーとの一時ファイルの受け渡しは `box/in/`
に置く（どちらも git 管理外）。

## なぜこの進め方か（2026-11-14）

それまでは「スパイクを回して記録を書き、節目でユーザーが継続・転換・中止を決める」形で進めていた。完全動的な
シーンの計測のあと、判断の材料が専門用語の表のままで、ユーザーが方向を決められなかった。また記録が増えるたびに
古い推測と方針が残り、次に何をするかが文書から一意に読めなくなった。この計画の決まりは、それを繰り返さないためにある。

- 次にやることは、いつも 1 つのフェーズのファイルに書いてある。
- 判断をユーザーに求めるときは、判断できる形（並べた画像と、平易な一文の意味）にして見せる。
- 終わったフェーズの記録と、外れた推測は残さない。

## 進め方

- 計画は作業の列ごとにディレクトリを分ける（`docs/plan/<列>/`）。列のディレクトリに、その列の `README.md`
  （フェーズの表、列で決めたこと、残り）とフェーズのファイルを置く。
- フェーズは 1 回のセッションで終えられる大きさにし、列の表の上から順に進める。今のフェーズは表の「次」。
- フェーズは 3 種類ある。
  - **auto**（`phase-NN-auto-<名前>.md`）：人の確認なしで最後まで進めるもの（実験、実装、計測）。ファイルの最初の
    `/goal` プロンプトで始める。
  - **review**（`phase-NN-review-<名前>.md`）：方向の確認。案と測った結果を比べて、ユーザーが方向を決めるもの。
    継続・方向転換・中止の判断は必ずこの種類で行う。ファイルの最初の開始プロンプトで始める。終わった時点で物は
    まだできていない。
  - **built**（`phase-NN-built-<名前>.md`）：できた物の確認。実装した結果をユーザーが実物（画像、連番、数値）で確かめ、
    気になる所の一覧を作って直し、OK をもらって終えるもの。ファイルの最初の開始プロンプトで始める。
- 挟み方：
  - 出力の画像を変える auto（レンダラの方式や既定値を変えるもの）の後には必ず built を置く。画像を変える auto を
    2 つ続けない。review で選んだ物も、作った後に built で確かめる。
  - 1 つの対策か 1 つの問いを 1 つのフェーズにする。
  - 計測だけの auto（画像を変えない）は続けてよい。
- 区切りが付いたら、今のフェーズのファイルの「やること」に、やったことと次にやることを書く。セッションの中で
  フェーズが終わらなければ、ファイルの開始プロンプトそのものを、次のセッションが続きから始める文に書き換える
  （どこから続けるか、決まった事、Artifact の URL）。ユーザーはプロンプトに文を足さず、そのまま貼る。
- そのフェーズで後のフェーズの計画が変わったら、まだ始めていない後のフェーズのファイルをまとめて書き直す。
  遠い先のフェーズは表の行だけか短く書いてあり、近づいたらファイルを作って詳しくする。
- フェーズを終えたら、残す決定と測った結果を正本（`docs/spec/`、コード、コメント）へ還元し、数値の要約を
  `docs/reference/measurements/<列>/` に置き、そのフェーズのファイルを消して、列の表から行を消す。
  完了したフェーズの記録は残さない（経過は git log にある）。外れた見立ては spec から消す（負の結果は
  「測った結果」として 1 行残す）。

## プロンプトの使い方

1. Claude Code を auto mode で起動する（`/goal` は権限モードを変えない）。
2. 新しいセッション（か `/clear` の後）で、フェーズのファイルの最初のプロンプトをそのまま貼る。進み具合は `/goal`
   （引数なし）で見て、止めるときは `/goal clear`。
3. 完了を判定するモデルはファイルを読まず、会話の内容だけで判断する。そのためプロンプトは、完了条件の各項目の根拠
   （コマンドの出力、数値、ファイルのパス、Artifact の URL、見た画像の一覧）を会話に示すことを求める。
4. `/goal` の実行中に文章で質問してターンを終えると、自動で再開してしまう。方向、スコープ、予算、見た目に関わる
   判断は必ず AskUserQuestion で尋ねる。軽い実装上の判断は自分で決め、最終報告に書く。

review（方向の確認）の進め方：

```text
1 準備     選べる案を 2〜4 つにまとめる。各案に「何が良くなり、何を失うか」を 1 行ずつ付ける。
           比べる画像（同じ画角、同じフレーム。動きは連番かちらつきの分布図）と数値を 1 枚のページにまとめ、
           非公開の Artifact に公開する。専門用語は最初に 1 文で説明する。AI の推奨は 1 つだけ、理由つきで書く
2 選択     AskUserQuestion で尋ねる（選択肢：各案 / 追加で材料を出してほしい）
3 追加     求められた材料を足して同じ URL へ再公開し、2 へ戻る（何回でもよい）
4 反映     決まった方向を spec に日付つきで書き、採らなかった案を消す。
           後のフェーズのファイルを、決まった方向で書き直す
```

built（できた物の確認）の進め方：

```text
1 準備     作った物を、そのフェーズの「確かめる決定」の数値で測る。
           前後の画像（同じ画角、同じフレーム）、ちらつきの分布図、数値、費用（ms、MB）を 1 枚のページにまとめ、
           非公開の Artifact に公開する。悪くなった所を隠さず、先頭に書く
2 確認     ユーザーが見て、気になる所を挙げる。採否はユーザーが決める
3 直す     一覧を直して測り直し、同じ URL へ再公開して 2 へ戻る
4 終える   AskUserQuestion で OK を取る（選択肢：OK / まだ直してほしい（どこを））
```

- AI はユーザーの回答なしにどの案も採用しない。数値が目安に届いたことを OK の代わりにしない。
- Artifact はフェーズごとに 1 つにし、同じ URL へ再公開する。URL はそのフェーズのファイルの「やること」に書く。
- Artifact は非公開のまま使う。このリポジトリは公開なので、Artifact に載せるのは計測の画像と数値だけにし、
  ローカルの絶対パスや個人の情報を載せない。
- 会話に全ログや画像データを貼らない。コマンドの出力は結果と保存先だけを示し、詳細は `box/out/` に残す。

## 共通の完了定義

各フェーズは、そのファイルの完了条件に加えて次を満たして終える。

- `mise run typecheck` と `mise run check` が通る。実行していない検査は「未実行」と書く。
- フェーズのファイルの「確かめる決定」の一覧を全部確かめ、結果を会話に示している。決定を黙って変えていない。
- 以前の数値を前提にした実験は、最初にその数値を再現している（再現しなければ止めて報告する）。
- 新しいシーン、新しい結果は、数値の前に画像を見ている。見た画像を会話に一覧で示している。
- 測った数値は「探索値」と明記し、条件（シーン、設定名、フレーム数、回数）を添えている。
- 予算（GI 4 ms、128 MB）と評価の指標を変えていない。判定の閾値を結果を見てから動かしていない。
- 画像を変えたフェーズは、次の built でユーザーの OK を取る（auto は測る所まで）。
- 決まったことと測った結果を `docs/spec/` へ還元し、数値の要約を `docs/reference/measurements/<列>/` に置き、
  使わなくなったコードと診断用のスイッチを消し、そのフェーズのファイルを消し、列の表を更新している。
- `box/out/` の生の出力は、要約を作ったら消している（参照の `box/out/mitsuba/` は残す）。
- `Co-` で始まるトレーラーを付けずにコミットし、`git status --short` が空（`.claude/` を除く）。push はユーザーに
  尋ねてから行う（公開リポジトリ）。
